How fast annotated validates, and what changed

annotated at git f881d35 against validator 0.21.0, garde 0.23.0, wary 0.3.2 and serde_valid 3.2.0. Measured on 12 November 2026 on an Intel Core i7-14700K pinned to one performance core, with rustc 1.99.1. Every library checks the same rules, written in its own syntax.

This run adds collecting deserialization. annotated::json::from_str reads a body and validates it in one pass. On flat bodies it runs on par with serde_json then validate(); on valid nested bodies it trails it by 1–4% with LTO. Collecting deserialization has the details, What changed sets this run beside the one before, and How it was measured says how far where the code lands moves the numbers.

What the numbers say
  • Flat bodies: on par. Either way annotated is about 1.36× ahead of the next library on the valid body.
  • collect_type_errors costs about a fifth on a valid body: 360.5 against 299.0 ns with LTO, 393.2 against 321.1 ns without. Its buffers borrow the strings serde_json lends, so it makes the same 6 allocations.
  • Failing fast answers the first violation in 206.3 ns with every field invalid, against 219.6 ns for serde_json then validate_fail_fast and 363.1 ns for every violation.
  • Valid nested bodies trail by 1–4% with LTO, 2–5% without. In repeated alternating runs of the same code the order ranged from +1.4 to +3.0% and the warehouse from +1.7 to +4.4% with LTO; in instructions, +2.1% and +1.7%. On the valid order annotated, validator and garde are within a run's noise of each other end to end: 7.85, 8.81 and 7.88 µs with LTO; 8.27, 8.22 and 8.73 µs without.
  • A map with invalid values keeps each value's violations apart until it has read them all, to report them in key order: 229 allocations against 224 on the warehouse with 5 invalid entries, 4.7% slower with LTO.
  • A body missing a field isn't like for like. json::from_str answers all three problems in 277.3 ns; through serde_json every library answers serde's error alone in 213.6 to 224.6 ns. The timings say what each answer costs.

Where the libraries mean different things

Eleven differences, and what each does to the numbers
  1. One failure per field, or every failure. annotated stops checking a field at its first broken rule; #[validate(report_all)] checks them all, like the others do. Only username breaks two rules, so annotated reports 8 violations there by default and 9 with report_all. Both are measured.
  2. What a length counts. annotated counts chars by default, and bytes or graphemes when asked; it settles a length by the byte length when that decides it, with the same answer counting gives. garde counts bytes by default and is asked for chars. validator counts only chars. serde_valid counts only graphemes, so its rows are labelled (graphemes).
  3. What an email address is. annotated checks the HTML form rule by hand. validator applies it with regular expressions and retries non-ASCII domains through IDNA. garde applies it with regular expressions. wary parses RFC 5322, which accepts more. All accept the valid address and refuse the invalid one used here.
  4. What a URL is. annotated accepts an absolute URI with an authority by RFC 3986, with RFC 3987's international characters, a non-empty host and no userinfo, of the scheme http, https or ftp, and recognizes it without parsing. validator, garde and wary accept anything url::Url::parse accepts, by the WHATWG URL Standard. At the edges they differ: annotated accepts http://256.0.0.1 and ports above 65535, and refuses URIs without an authority, like mailto: addresses. All accept the valid URL and refuse the invalid one used here.
  5. required is used only on an Option, where it means Some in every library.
  6. Patterns use the same regex build everywhere, each compiled once into a static.
  7. What a violation holds differs, and is part of what's measured. annotated's is 176 bytes, its path kept in place for up to three segments. validator, for instance, copies each failing field's value into its error as JSON.
  8. Maps. wary can't go through maps. Only annotated checks a map's values with their own rules, so it's alone in that card.
  9. A wary bug: 0.3.2 reports the missing fullName under the path username. It still does the same work.
  10. End to end, annotated reads two ways. serde_json, then validate is serde's derive then validation, as every other library does. json::from_str checks each field as it reads it, and would report a missing field beside the broken rules. On a complete, well-typed body both find the same violations, so they compare like for like. The fail-fast cases answer one violation; compare them with each other. collect_type_errors reads each field into a buffer first, to report a value of the wrong type; on a body without one it finds the same.
  11. The missing-field body isn't like for like. json::from_str reads the body without its postalCode, checks what came and answers 3 violations. serde stops at the missing field, so through serde_json::from_str no library validates: each answers serde's error alone, counted as one problem. The timings show what each answer costs, not which library validates faster.

How it was measured

Environment, and how far to trust the numbers
CPUIntel Core i7-14700K, pinned to CPU 4 (a performance core) with taskset. Its sibling thread wasn't isolated.
Clockintel_pstate, governor powersave (hardware-managed), balance_performance, turbo and SMT on
Kernel, toolchainLinux 7.3.3-1-cachyos-bore, rustc 1.99.1 (58cf8f9c3 2026-10-13)
ProfilesWith LTO: opt-level = 3, lto = "fat", codegen-units = 1. Without LTO: cargo's release defaults, 16 codegen units.
Harnesscriterion 0.8.2: 100 samples, 0.5 s warm-up, 2 s of measurement per case, within a run's own spread of criterion's 3 s and 5 s. Allocations counted by a global allocator in a separate binary, over 10,000 validations after 100 warm-up ones.
LoadA desktop session, load average about 1.0 to 1.5. No compiler ran during the runs.
  • 126 of the 129 medians, with LTO and without, have a 95% confidence interval within 1% of them; all are within 3.7%. Invalid paths move up to about 15% between runs of the same code, as the allocator's state differs. Compare libraries within a run, not nanoseconds across runs.
  • Where the code lands moves annotated's valid paths by up to 18%. map_nested_valid reads 144.8 ns here against 122.7 ns at 99972e3, with byte-identical code at another offset of its cache line. Timed in one session, both revisions built with every function and jump target aligned to 64 bytes are within 2.4% of each other on every valid path over structs (map_nested_valid 121.1 against 122.8 ns); built as the README says, 122.3 against 144.7 ns. RESULTS.md has the control's table.
  • No hardware profiler was available. Instruction counts were read through perf_event_open in a probe kept out of the repository; the explanations come from them, the expanded derive code, the machine code, and the experiments.
  • To rerun: taskset -c 4 cargo +1.99.1 bench --bench validation, then cargo +1.99.1 run --release --bin allocations and --bin report. The README has the rest.
