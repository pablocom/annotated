## [0.1.0] - 2026-11-12

### Added

- The `Validate` trait, with `validate()` answering every violation found, and the error model it reports with: `Violations`, `Violation`, `Problem` with its stable `code()` and `params()`, each param a `ParamValue`: an integer, a float or a text, `Path` with `json_pointer()`, and `Location` and `FoundViolations` for implementing `Validate` by hand.
- The `Rule` trait and the first built-in rules in `annotated::rules`: `required`, which checks anything implementing the `Required` capability trait, and `length`, which counts the `char`s of a string, or its bytes with `in_bytes()` and its grapheme clusters with `in_graphemes()` behind the `unicode` feature, and the elements of anything implementing `HasLength`.
- `#[derive(Validate)]`, re-exported by `annotated`. Rules are written in `#[validate(...)]` on fields: a built-in rule by name, your own by path, given a constructor value (`name = value` or `name(value)`) or named builder arguments (`name(key = value)`), and a `message` override with `{param}` placeholders. Every field is checked, stopping at a field's first broken rule unless the struct has `#[validate(report_all)]`. On an `Option` field, `required` checks the `Option` and every other rule the value inside. Fields are reported by the name serde reads them by, under `rename_all` and `rename`.
- The `range` rule: a value no less than `min` and no more than `max`, for anything `PartialOrd` and `Display`, with the bounds' type taken from the field. Bounds of a primitive number type are reported as numbers, and those of any other type as text.
- The `email` rule: an email address as HTML's `<input type="email">` accepts one, at most 254 bytes.
- The `url` rule: an absolute URI with a host by RFC 3986, with RFC 3987's international characters, and without userinfo, whose scheme is `http`, `https` or `ftp`, or one of those set with `schemes`, compared ignoring case. It allocates nothing.
- The `ip`, `ipv4` and `ipv6` rules: an IP address of either version, or only of version 4 or only of version 6, each reporting a problem coded by its own name.
- The `contains`, `prefix` and `suffix` rules: a string containing, starting with or ending with a text.
- The `custom` rule: any `Fn(&V) -> Result<(), Problem>` of your own, checking any value that borrows as a `V`, so a check of `&str` checks a `String` field. It reports with `Problem::custom`, whose `with_param` takes a number or a text.
- The `pattern` rule, behind the `regex` feature: a string matching a regular expression. Written in `#[validate(...)]`, the expression is a string literal checked at compile time and compiled once, into a `static` at the field.
- `nested`, which validates a field implementing `Validate` under the field's name, and `each(...)`, which applies its rules to every element of a collection at its index, or every value of a map at its key, through the `HasElements` capability trait, also behind a reference or a `Box`, like `&'a [T]` or `Box<[T]>`. `each(nested)` validates every element, and `each` nests.
- Struct-level `#[validate(custom(f))]`: any `Fn(&Self) -> Result<(), Problem>`, checked after every field and reported at the struct's own location, or at a field by its serde name with `custom(f, field = name)`. Several are allowed, checked in the order written, beside `report_all`. One at a field counts as that field's last rule, so it is skipped once the field has a violation, unless the struct has `report_all`.
- `Validate::validate_fail_fast()`, which answers only the first violation: the first that `validate()` answers, even under `report_all`. Checking stops right after it, except that a nested value finding it doesn't stop the struct around it at once: that struct records nothing more and stops at its own next violation or its end. For implementing `Validate` by hand, `FoundViolations::failing_fast()` starts such a report, `is_finished()` answers whether it has its violation, and a finished report records nothing more. `HasElements::for_each_element`'s `check` now answers whether to go on, and the elements after one it answers `false` for are skipped.
- `Problem::Missing`, code `missing`, read as `is missing`: a field absent from the input being deserialized.
- `Problem::InvalidType`, code `invalid_type`, read as `must be {expected}, found {found}`: a value of the wrong type for its field, with the params `expected`, what the field's type accepts as serde describes it, and `found`, the kind of value that came (`string`, `integer`, `null`, …), never the value itself.
- The `serde` feature, on by default, and with it the `Deserialize` trait for collecting deserialization: `deserialize_at` reads a value at a location and pushes every violation in it into a `FoundViolations`, answering the value, `None` when it couldn't be built, or the format's own error. `from_deserializer` reads a value from the root and answers it, or a `DeserializeError`: the format's error, or every violation found, which `violations()` answers as a slice either way. `from_deserializer_fail_fast` answers only the first violation.
- `#[derive(Deserialize)]`, behind the `serde` feature, for a struct with named fields: it implements `annotated::Deserialize`, and serde's `Deserialize` through it, reading the struct by serde's names, under `rename_all`, `rename` and `alias`, with `deny_unknown_fields` and `expecting`. Once the input is read, every field is checked in declaration order: a field absent from the input is `Problem::Missing`, unless it's an `Option`, which is `None`, and a field that came is checked by its rules as `Validate` checks it. Struct-level rules run last, when every field came. serde's `Deserialize` refuses a struct breaking its rules with every violation in its error's message. Other `#[serde(...)]` attributes and lifetime parameters are refused at compile time for now.
- `annotated::Deserialize` for the containers a nested value is held in: `Option<T>`, `Box<T>`, and `Box<[T]>`, `Vec<T>` and `VecDeque<T>`, reading each element at its index, and `BTreeMap<K, V>` and `HashMap<K, V, S>`, reading each value at its key, built only when everything in them is. A map reports its values' violations in the order it goes through them, and a value given again for a key replaces the one before, with its violations. A sequence or a `HashMap` reserves room for the values the format says it holds, up to a megabyte, as serde does. For implementing `annotated::Deserialize` by hand, `FoundViolations::new_alike` starts a report of a part of a value, gathering as its parent does, and `append` moves its violations into the parent.
- `#[derive(Deserialize)]` reads a field checked with `nested`, or with `each(...)` holding `nested` at any depth, through `annotated::Deserialize`, so a field missing inside it is reported at its full path, beside its broken rules, in the order `Validate` reports them. A nested value that couldn't be built reports its violations and skips its field's other rules and the struct-level rules around it. Failing fast still answers the first violation of the full report: a struct whose fields all came is built even once its report is finished, so the value around it can check it. A field's rules can name `nested` once.
- `#[derive(Deserialize)]` accepts and ignores the `#[serde(...)]` attributes that only change serializing, so a struct can derive serde's `Serialize` beside it: `into` and `bound(serialize = "...")` on the struct, `skip_serializing`, `skip_serializing_if`, `serialize_with`, `getter` and `bound(serialize = "...")` on a field. Those that change reading stay refused.
- `#[annotated(collect_type_errors)]` on a struct deriving `Deserialize`: each field is read in two steps, first into a buffer holding any well-formed value, borrowing the strings and bytes the format lends, then from the buffer as the field's type, so a value of the wrong type is `Problem::InvalidType` at the field, beside the other violations in declaration order, instead of the format's error. `expected` is what serde says the type expects, or, when the type refuses the value with a message of its own, the type's name (the one inside an `Option`); for a value inside the field, such as an element of a list, both params describe that value. A value of the wrong type is checked by no other rule and skips the struct-level rules; inside a nested value, it replaces the violations found there before it, and a nested struct collecting them too reports those inside it at their full paths. Failing fast still answers the first violation of the full report. Map keys written as strings, as JSON writes every key, are read as the integers or booleans their type asks for, as `serde_json` reads them. It needs a self-describing format. Any other option in `#[annotated(...)]`, and any option on a field, is refused at compile time.
- The `json` feature, which adds `serde_json` and turns on `serde`: `annotated::json::from_str` and `from_slice` read a JSON document collecting every violation in it, refusing characters after the value as `serde_json` does, before answering any violation, and `from_str_fail_fast` and `from_slice_fail_fast` answer only the first violation.
- `examples/axum`, an axum extractor to copy into your app: it reads a JSON body with `annotated::json::from_slice`, refuses a request it can't read as axum's `Json` does, and answers every violation with 422 as RFC 9457 problem details, each with its JSON Pointer, code, params and message.
